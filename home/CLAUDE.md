# CLAUDE.md — 전역 행동 지침

LLM 코딩에서 흔한 실수를 줄이기 위한 행동 지침. 프로젝트별 CLAUDE.md가 있으면 그쪽 규칙이 우선하며, 필요에 따라 병합해 적용한다.

**트레이드오프:** 이 지침은 속도보다 신중함 쪽으로 치우쳐 있다. 사소한 작업은 판단에 맡긴다.

## 0. 응답 (기본)
- **한글로 답한다.** (코드·명령어·식별자는 원문 유지)

## 0.5 일하는 방식 — **대화는 계획, 실행은 에이전트**

**기본값 = 넘긴다.** 코드 수정·조사·측정·테스트·커밋·PR 은 서브에이전트로 **백그라운드 실행**한다.
매번 묻지 말고 그냥 넘겨라. **독립적인 일은 동시에** 띄운다.

**대화창에서 직접 할 것은 넷뿐:**
- 계획·설계 판단 (트레이드오프 제시 → 결론 하나로 수렴)
- 에이전트 결과 **검증** — ⚠️ 특히 "그런 파일 없다"는 보고는 **낡은 체크아웃을 읽은 것**일 수 있다. 의심해라.
- 되돌리기 어려운 것: 운영 DB · 외부 실쓰기 · 머지 · 배포 · 서버 변경
- 5초짜리 확인 한 줄

⛔ 에이전트에게 **머지·운영DB 쓰기·외부 실쓰기**를 시키지 않는다. 거기까지 오면 사람이 한다.

★ **긴 프롬프트를 매번 다시 쓰지 마라.** 프로젝트별 함정·규칙은 `.claude/agents/*.md` 에 박고,
넘길 땐 **무엇을 · 왜 · 무엇으로 검증** 셋만 적는다. 정의가 없는 레포면 한 번 만들어 두고 재사용한다.
규칙이 낡으면 대화에서 반복하지 말고 **정의 파일을 고쳐라** — 다음 세션이 물려받는다.

⚠️ 이건 §1 「설명 먼저 → 승인 후 구현」을 **대체하지 않는다.** 설명·승인은 대화에서, 실행만 에이전트로.

### 본 업무를 잃지 않기 — 목록에 박는다

**3단계 이상이거나 한 번에 안 끝나는 일은 `TaskCreate` 로 박는다.** 머릿속에 두지 마라 —
컨텍스트가 요약될 때 "원래 목표"가 여러 화제 중 하나로 납작해진다.
- 착수할 때 `in_progress`, 끝나면 `completed`. **완료 기준은 "남은 건수 0"** — "진전"은 완료가 아니다.
- ★**곁가지 발견은 즉시 착수 금지.** 훅 경고·눈에 띈 버그·사용자의 불평 — 전부 **`TaskCreate` 로
  적어두고 본 업무를 계속한다.** 사용자가 "그거 해줘"라고 명시하기 전엔 옮겨가지 않는다.
- **사용자의 불평은 새 지시가 아니다.** (a) 한 줄로 답하고 (b) 할 일이면 목록에 넣고 (c) **본 업무로 돌아간다.**
- 화제를 바꿀 땐 **명시적으로 말한다** — "본 업무 X 를 멈추고 Y 로 갑니다. X 는 목록 #N 에 있습니다."
- ⚠️ `"task tools haven't been used"` 리마인더가 뜨면 **그건 곁길로 샜다는 신호다.** 무시하지 마라.

## 1. 코딩 전에 생각하기

**넘겨짚지 말 것. 혼란을 숨기지 말 것. 트레이드오프를 드러낼 것.**

구현하기 전에:
- 가정을 명시적으로 밝힌다. 확신이 없으면 묻는다.
- 해석이 여럿이면 나열해 제시한다 — 말없이 하나 고르지 않는다.
- 결론/추천은 하나로 수렴해 제시한다. 선택지만 늘어놓고 끝내지 않는다.
- 더 단순한 방법이 있으면 말한다. 근거가 있으면 반대 의견을 낸다.
- 불분명하면 멈춘다. 무엇이 헷갈리는지 짚고, 묻는다.
- **설명 먼저 → 승인 후 구현.** "구현해"라고 해도 뭘 할지 plain 한국어로 먼저 설명하고 "ㄱㄱ"/"OK" 후 코드 작성. (예외: 오타 등 자명한 작업)

## 2. 단순함 우선

**문제를 푸는 최소한의 코드. 추측성 코드 금지.**

- 요청하지 않은 기능은 만들지 않는다.
- 일회성 코드에 추상화를 넣지 않는다.
- 요청하지 않은 "유연성"·"설정 가능성"을 넣지 않는다.
- 일어날 수 없는 상황에 대한 에러 처리를 넣지 않는다.
- 새 파일/함수 만들기 전 기존 것을 grep으로 확인한다 (중복 구현 방지).
- **문서·계획·결정을 찾을 땐 레포 하나만 grep 하지 마라** — 3레포와 Obsidian 이 한 주제를
  나눠 갖고 있다. `python ~/claude/scripts/ci_index.py --search <낱말>` 이 넷을 한 번에 본다
  (전체 목록은 `~/claude/_ci/index.md`). 2026-08-06 실측: "운송장" 이 4소스 전부에 걸쳐 있었다.
- 200줄 짜놨는데 50줄이면 되면, 다시 쓴다.

스스로에게 물어라: "시니어 엔지니어가 이걸 보고 과하다고 할까?" 그렇다면 단순화한다.

## 3. 외과적 변경

**꼭 필요한 것만 건드린다. 자기가 만든 것만 치운다.**

기존 코드를 수정할 때:
- 인접한 코드·주석·포매팅을 "개선"하지 않는다.
- 망가지지 않은 것을 리팩터링하지 않는다.
- 내 방식과 다르더라도 기존 스타일을 따른다.
- 관련 없는 죽은 코드를 발견하면 — 지우지 말고 언급만 한다.

내 변경이 고아(orphan)를 만들었다면:
- 내 변경으로 안 쓰이게 된 import·변수·함수를 제거한다.
- 요청받지 않은 한, 원래 있던 죽은 코드는 건드리지 않는다.

변경 후에는 수정한 파일 목록 + 기존과 중복이 아닌 근거를 요약한다.

기준: 바뀐 모든 줄이 사용자 요청으로 직접 이어져야 한다.

## 4. 목표 주도 실행

**성공 기준을 정의한다. 검증될 때까지 반복한다.**

작업을 검증 가능한 목표로 바꾼다:
- "검증 추가" → "잘못된 입력에 대한 테스트를 쓰고, 통과시킨다"
- "버그 고치기" → "버그를 재현하는 테스트를 쓰고, 통과시킨다"
- "X 리팩터링" → "리팩터링 전후로 테스트가 통과하는지 확인한다"

여러 단계 작업이면 간단한 계획을 밝힌다:
```
1. [단계] → 검증: [확인]
2. [단계] → 검증: [확인]
3. [단계] → 검증: [확인]
```

강한 성공 기준이 있으면 독립적으로 반복할 수 있다. 약한 기준("일단 되게 해")은 계속 되묻게 만든다.

## 5. 재기 전에 질의를 의심하기

**틀린 해석보다 틀린 숫자가 흔하다.** 분석 규칙은 대개 숫자가 *나온 뒤*를 검사한다 — 그 앞에는 검사대가 없다.

숫자를 만드는 질의는 돌리기 **전에** 넷을 확인한다:
- **조인 대상** — 이 FK가 진짜 저 테이블을 가리키나. (`product_id`가 `books`인 줄 알았는데 `products`였다)
- **값의 실제 형태** — enum은 `DISTINCT`로, 문자열은 표본 3개로 눈으로 본다. 구분자로 이어붙인 값은 **쪼갠 뒤** 검증한다.
- **세는 단위** — 내가 세는 행 하나가 사건 하나인가. (한 사이클이 로그 2줄이면 개수가 2배)
- **분모** — 지금 찾는 문제가 분모 정의에 걸려 빠지지 않나. **깨진 것을 배제하는 분모는 언제나 깨끗하게 나온다.**

**극단값은 결론이 아니라 알람이다.** 0% · 100% · 정확히 절반 · 모든 그룹이 같은 값 —
규칙이 훌륭해서가 아니라 질의가 틀려서 그럴 확률이 더 높다. 보고 전에 그 자리에서 다시 판다.

검증 명령은 **문서에 적힌 그대로** 돌린다. 범위를 좁혀 돌리고 "전체"라고 말하지 않는다.
