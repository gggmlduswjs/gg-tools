현재 변경사항을 **문서 준수 + 운영 안전** 관점으로 리뷰하라. 코드는 수정하지 않는다.

역할 분담 (2026-09-01 정리):
- **여기** — 프로젝트 축. 아키텍처·규칙·운영/데이터 안전·에러 처리·테스트.
- **내장 `/code-review`** — 범용 축. 정확성 버그 + 재사용·단순화·효율. effort 조절·`--fix`·`--comment` 가 붙는다.
- **레포별 보안 스킬**(`<repo>-security-scan` 등) — 보안 축. 레포 전체가 대상이라 diff 보다 넓다.
⛔ 여기서 정확성 버그를 사냥하지 마라 — 내장이 검증까지 하고 온다. 중복이면 그쪽이 이긴다.

먼저 다음을 읽어 기준을 잡아라:
- `CLAUDE.md` (작업 방식 · 운영 변경 · 데이터 안전 · 코드 규칙)
- `AGENTS.md` (있으면)
- `docs/ARCHITECTURE.md` 또는 동등한 구조 문서
- `docs/ADR.md` / `docs/_ai/adr/` (있으면 — 필요한 본문까지)

리뷰 대상 diff: 인자 `$ARGUMENTS`가 있으면 그 PR/브랜치/경로, 없으면 `git diff HEAD` + `git status --short`.

## 체크리스트

1. **아키텍처 준수** — 새 코드가 기존 계층·도메인 자리에 있는가? CLAUDE.md/ARCHITECTURE 경로 규약을 따랐나?
2. **중복 구현 방지** — 같은 일을 하는 기존 함수/서비스/뷰가 있는데 새로 만들었나? `rg` 근거 있나?
3. **운영 안전** — 운영 변경이 레포가 정한 배포 경로만 타는가? 수동 migrate·prod DDL·서버 직접 편집·실쓰기(`--apply`)가 diff에 없나?
4. **데이터 안전** — 대량 수정 전 백업/dry-run·소프트삭제 우선 등 CLAUDE.md 규칙을 지켰나?
5. **프로젝트 전용 게이트** — 해당 레포 `CLAUDE.md`에 적힌 체크리스트(간편주문·WING·세트물 등)를 해당 파일이 바뀌었을 때만 적용했나?
6. **에러 처리** — 시스템 경계(외부 API·사용자 입력·파일·DB)에서만 검증하나? 내부에 과한 try/catch 는 없나? **삼키는 except/빈 catch** 가 없나? 실패가 조용히 통과하지 않나?
7. **테스트** — 변경 모듈에 레포 정본 테스트 명령이 통과하나? 새 기능에 검증이 있나? 비즈니스 로직과 side effect 가 갈려 있어 **테스트할 수 있는 모양**인가?

## 출력 형식

| 항목 | 결과 | 비고 |
|------|------|------|
| 아키텍처 준수 | ✅/❌/N/A | {상세} |
| 중복 구현 방지 | ✅/❌ | {rg 근거 or 위반} |
| 운영 안전 | ✅/❌ | {상세} |
| 데이터 안전 | ✅/❌/N/A | {상세} |
| 프로젝트 전용 게이트 | ✅/❌/N/A | {상세} |
| 에러 처리 | ✅/❌/N/A | {상세} |
| 테스트 | ✅/❌ | {상세} |

위반(❌)마다 **CLAUDE.md/ADR의 해당 규칙을 인용**하고 구체적 수정 방안을 제시하라. 규칙을 못 찾으면 스타일 취향으로 지적하지 마라.
