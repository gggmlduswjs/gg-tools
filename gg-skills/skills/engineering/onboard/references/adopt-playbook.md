# 기존 프로젝트 도입 플레이북

이미 운영 중인 프로젝트에 하네스 틀(`ai-dev-harness`)을 입힐 때, **계획을 한 번에 세우는** 절차다. 스킬은 측정·질문·계획서까지만 하고 실행하지 않는다. 사용자 피드백은 Step 1 한 번과 아래 「사람 결정 지점」에서만 받는다. 프로젝트 정본 규칙(`CLAUDE.md`·`AGENTS.md`)이 harness 지침보다 우선하며, 충돌하는 harness 지침은 계획에서 뺀다.

## Step 0. 측정 (읽기 전용)

1. 아래 명령을 한 번씩 돌려 **처음 측정값을 기록해 둔다.** (스냅샷 기능은 아직 없다. 출력의 요약 숫자를 계획서 부록에 표로 옮겨 적는다.)
   ```
   python scripts/check_setup.py --catalog
   python scripts/check_setup.py --structure
   python scripts/check_setup.py --adopt <프로젝트경로|sources.yaml 이름>
   ```
2. 구조 변경이 후보에 오르면 대상 경로·모듈 문자열마다 `--impact` 로 참조·운영 접점 걸림을 본다.
3. 프로젝트의 `CLAUDE.md`·`AGENTS.md`·`.claude/rules/` 를 읽는다(프로젝트가 `sources.yaml` 에 있으므로 허용).

## Step 1. 결정 질문서

[decision-questionnaire.md](decision-questionnaire.md) 의 Q1~Q10 을 후보 답과 함께 **한 번에** 묻는다. 답은 계획서 맨 앞 「고정 결정」 표에 박는다.

## Step 2. 계획서

Phase 표에서 선행·병렬을 반영해 PR 단위 목록을 만든다. PR 마다 완료 기준·롤백·승인자를 채운다(`--adopt` 의 빈칸 `[ 승인 지점 ]` 을 질문서 답으로). 계획서는 사용자가 PR 로 넣는다. 스킬이 대상 프로젝트 안에 파일을 만들지 않는다.

| Phase | 내용 | 선행 | 병렬 가능 | 완료 기준 | 사람 결정 지점 |
|---|---|---|---|---|---|
| P0 | 측정·질문서·고정 결정 표 | 없음 | - | 처음 측정값 기록, 고정 결정 표 확인 | Q1~Q10 |
| P1 | 문서: 틀 채우기(필수 문서·섹션) | P0 | 문서 묶음별 | `--structure` 의 틀 `없음` 이 0 이거나 Q8 에 이유 기재 | 정본이 둘인 주제의 정본 지정, 유지/삭제(Q7) |
| P2 | 경로 하드코딩 제거(변수화) — 구조 변경의 선행 조건 | P0 | 워크플로·스크립트·설정 묶음별 | `--impact` 로 본 옛 경로 직접 참조 0, 동작 동일 검증 통과 | 서버 유닛·배포 설정 변경 승인 |
| P3 | 구조 변경(폴더 분리·이동·개명). **Q6 이 허용일 때만** | P2 | 서로 다른 영역끼리. 한 PR 에 두 영역을 섞지 않는다 | 옛 경로 grep 0, 필수 통과 항목(Q9) 녹색, 운영 접점 걸림 해소 | 컷오버 시각(Q5), 서버 접점 승인 |
| P4 | 문서·폴더 정렬 | P3 (Q6 허용 시) | 문서 이동 ∥ 코드 이동(참조 없는 것부터) | 구조 밖 문서 중 `참조됨` 제외 잔여가 목표치 이하 | 이동·삭제 대상 확정(Q7) |
| P5 | 코드 정리(죽은 코드·중복). **Q6 이 허용일 때만** | P3, 테스트 안전망 | 모듈별 | 테스트 통과, 동작 변경 0 | 삭제 승인(Q7) |
| P6 | 마감: 같은 명령으로 재측정·비교, 잔여 부채 등록 | P1~P5 | - | 아래 「완료 판정」 | 완료 선언(사용자) |

규칙
- 한 PR = 한 변경. 동작 보존과 동작 변경을 섞지 않는다. P2 를 구조 변경과 같은 PR 에 섞지 않는다.
- Q6 이 `no` 이거나 미답이면 P3~P5 를 계획에 넣지 않는다.
- 일정·담당·진행은 Q1 의 SSOT 에만 둔다. 계획서에 쓰지 않는다.

## 실행

스킬은 실행하지 않는다. 사용자가 계획서를 승인한 뒤, PR 단위로 에이전트나 사람이 작업 브랜치에서 진행하고(superpowers `writing-plans` + 프로젝트의 실행 에이전트), 머지는 Q2 의 권한자가 한다.

## 완료 판정 (P6)

같은 명령(`--catalog`·`--structure`·`--adopt`)을 다시 돌려 Step 0 의 기록과 **표로 비교**한다. 스크립트가 완료를 선언하지 않는다. 사람이 아래를 확인하고 선언한다.

- [ ] 처음보다 악화된 지표가 없다(없으면 "없음", 있으면 사유)
- [ ] `--structure` 의 틀 `없음` 과 `--catalog` 의 `확인` 이 0 이거나, 남은 항목마다 Q8 의 제외 이유가 있다
- [ ] 서버 접점이 있으면 배포 워크플로의 `concurrency` 유무를 확인했다(아래 R1)
- [ ] 미해결 항목은 사유와 함께 Q1 의 SSOT 에 등록됐다
- [ ] 사용자가 비교표를 보고 완료를 선언했다

## 서버 접점 위험 체크리스트

서버 접점이 있는 프로젝트(Q5)에서 구조 변경·컷오버를 계획할 때 계획서에 붙인다. 서버 쪽 값은 스킬이 볼 수 없으므로 `미확인`으로 두고 사람이 확인한다.

| # | 확인 | 근거 |
|---|---|---|
| R1 | 배포 워크플로가 `concurrency:` 그룹을 쓰는가(없으면 컷오버 중 두 배포가 겹칠 수 있다) | 워크플로 파일, `--impact` 운영 접점 |
| R2 | 컷오버 PR 머지 시각이 타이머·cron 발화 시각과 겹치지 않는가(시간대: Actions 는 UTC, systemd 는 유닛의 표기) | 서버·유닛 파일(저장소 밖이면 `미확인`) |
| R3 | 서버 유닛·cron 이 옛 경로를 직접 부르는가 | 서버(`미확인`) |
| R4 | 배포 직전·직후 타이머 정지/재개 절차가 있는가 | 프로젝트 문서 |
| R5 | 롤백 방법(이전 커밋 재배포)과 걸리는 시간 | Q5 |
| R6 | 컷오버·개명 PR 은 한 번에 하나, 실패하면 후속 PR 을 멈추는가 | 위 규칙 |

머지 직전에는 진행 중인 배포 실행이 없는지, 머지 직후에는 배포 결과와 타이머 상태를 프로젝트가 정한 확인 명령으로 본다(명령은 Q9·Q5 답에서 가져온다).
