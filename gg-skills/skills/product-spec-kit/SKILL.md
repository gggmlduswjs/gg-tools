# product-spec-kit — PRD·기능명세서·유저플로우·와이어프레임 한 세트

챗 기반 기획 SaaS(4탭 + AI챗)를 흉내내되, 그 도구의 진짜 가치(대화형으로 계속 고치는 것)는 **이 대화 자체**로 대체한다. 앱을 새로 만들지 않는다 — Artifact 하나를 같은 URL로 계속 재발행하는 것으로 충분하다.

**묻지 말고 초안부터 던진다.** 기획 SaaS가 잘 나오는 이유는 대충 말해도 일단 그려주기 때문이다. 가정은 문서 맨 위 "가정" 블록에 명시하고, 틀리면 대화로 고친다.

## 워크플로 (고정 5단계)

1. **코드 리서치 먼저** — 대상 기능의 실제 뷰·템플릿·서비스 파일을 Grep/Glob/Read로 찾는다. PRD의 "문제" 섹션은 **반드시 이 리서치에서 나온 실측 갭**이어야 한다. 코드를 못 찾았거나 확인 안 된 문제는 쓰지 않는다.
   **git 레포라면 워킹트리가 아니라 `origin/main`을 본다** ↓ (아래 "근거는 origin/main" 참고)
2. **이 스킬 자체의 에셋으로 디자인 플랜을 잡는다.** `assets/shell.html` 구조를 재사용하되 이번 주제에 맞는 색 4~6개·타이포 계층·레이아웃을 먼저 정하고 `:root` 토큰을 교체한다. 별도 `artifact-design` 스킬은 **선택적 보조도구**다. 설치되어 있지 않아도 이 스킬이 실패하거나 중단되어서는 안 된다.
3. **4개 섹션을 한 Artifact HTML에** 사이드바 탭으로 담는다. 각 섹션 최소 기준은 "섹션별 하한선" 참고.
4. **사용 가능한 전달 방식으로 발행** — Artifact 기능이 있으면 링크를 사용하고, 없으면 생성한 HTML 파일 경로를 전달한다. 지원되지 않는 도구를 있다고 가정하지 않는다.
5. **대화로 반복 수정** — "OO 다시" 하면 해당 섹션만 고쳐 **같은 file_path로 재호출**(다른 세션이면 `url` 파라미터로 지정).

## 근거는 origin/main — 이걸 어기면 문서가 거짓말을 한다

로컬 브랜치가 뒤처져 있으면 **이미 배포된 기능을 "개선 제안"으로 쓰게 된다.**
2026-07-27 실사고: 요구사항 3건을 제안으로 적었는데 셋 다 main에 배포돼 있었다(`a041fb7e`·`6999141e`·`859d42a1`).

```bash
git ls-tree -r --name-only origin/main | grep <기능키워드>     # 파일 찾기
git log origin/main --oneline -20 -- '*<기능키워드>*'          # 최근 변경 = 이미 한 일
git show origin/main:<경로> | sed -n '300,400p'                # 실제 코드 읽기
```

커밋 로그에 제안하려던 내용이 이미 있으면 → **"제안"이 아니라 "현행"으로 적는다.**
PRD에 "이미 해결된 것"(제안 → 배포됨 + 커밋 해시) 표를 따로 두고, **현행과 제안을 절대 섞지 않는다.**

## 섹션별 하한선 (이거 밑으로 만들면 "부실하다"는 피드백을 받는다 — 실측)

### PRD
개요(한줄정의·제품목표) + **현행 구성**(화면 위→아래 순서 그대로, 영역마다 코드 인용) + **이미 해결된 것** + 문제/해결(각 문제에 코드 근거 한 줄 필수, 최소 3개) + 타겟/시나리오 + **범위 밖** + **열린 질문** + 성공지표·위험요소.

- 문제 하나짜리, 범위밖·열린질문 없는 PRD는 하한선 미달.
- 근거 없는 문제 제기는 **삭제한다**. "헷갈릴 것 같다"는 문제가 아니다.
- 문제 우선순위는 UX 편의가 아니라 **돈이 잘못 기록될 위험** 순.
- 사용자·의사결정자의 기존 지시와 충돌하는 개선은 제안이 아니라 **열린 질문**으로 올린다.

### 기능명세서 — 셋 다 만든다
1. **마인드맵** — `assets/mindmap.html`을 통째로 붙이고 `TREE` 하나만 교체.
   `PRD ─ 요구사항 ─ 기능 ─ 세부`. 돈·되돌릴 수 없는 것은 `hot:true`(빨강).
2. **우선순위/의존관계/리스크 매트릭스 표** — 카드 목록 **위에** 별도로.
3. **요구사항 카드** — ID·우선순위·설명·수용기준·영향 파일·리스크.

- 카드만 나열하고 매트릭스 없는 건 하한선 미달.
- 요구사항 ID는 PRD의 문제와 **1:1 대응**. 대응 없는 요구사항은 지운다.
- 수용기준은 **검증 가능한 문장**으로. "편해진다" ✗ → "스크롤해도 컬럼 헤더가 보인다" ✓
- 마지막에 **구현 순서**를 제안한다. 돈 경로는 맨 마지막 단독 커밋.

### 유저플로우 — mermaid 쓰지 말 것
mermaid `flowchart LR`+`subgraph`는 레인 개념이 없어 스윔레인이 안 나온다.
캔버스가 본문 폭에 잘리고 레인 제목이 붙지 않아 **"다 안 보인다"는 피드백을 받았다**(실측).

`assets/swimlane.html`을 통째로 복사하고 `LANES` / `N` / `E` 세 배열만 교체한다.

- `LANES` — **업무 구간**으로 자른다(화면 요소로 자르면 IA와 중복). 5~7개.
- `N` — `{id, l:레인, c:열, r:줄, t:타입, x:'라벨', s:'부제'}`
  타입: `entry` · `screen` · `sub` · `''`(단일 조작) · `warn` · `danger`(되돌릴 수 없는 조작)
- `E` — `[['from','to'], ...]`
- **되돌아오는 화살표를 반드시 넣는다.** 고치러 나갔다 같은 조건으로 복귀하지 못하면 사용자는 헤맨다.

### 와이어프레임
**최소 2개, 권장 3~5개 화면 상태**(기본 + 엣지 하나 이상 — 빈 결과·펼침·에러)를 탭으로 전환.
브라우저 크롬으로 감싸고, 변경 지점에 번호 콜아웃 → 하단 "변경 로그"와 매칭.

- 상태 1개만 그린 건 하한선 미달.
- **현행 레이아웃을 그대로 그린다.** 새 화면을 발명하지 않는다.
- **"여긴 이미 맞으니 손대지 말자"는 상태도 넣는다.** 안 바꿀 곳을 남겨야 다음 사람이 안 건드린다.

## 에셋

| 파일 | 용도 |
|---|---|
| `assets/shell.html` | 4탭 껍데기(사이드바·탭전환·기본 CSS). `{{...}}` 채우고 `:root` 팔레트는 매번 새로 |
| `assets/mindmap.html` | 기능 분해 트리. `TREE` 교체 |
| `assets/swimlane.html` | 유저플로우 스윔레인. `LANES`/`N`/`E` 교체 |
| `assets/mm_layout.test.js` | 트리 좌표 검증. `node` 로 실행 — 렌더러를 손댔으면 돌린다 |

## 함정 (전부 밟아봤다)

| 증상 | 원인 | 대응 |
|---|---|---|
| 선이 한 점에 뭉침 | 비활성 탭은 `display:none` → `offsetLeft/Top`이 전부 0 | 렌더러가 좌표를 **데이터로 계산**. 오프셋 읽지 말 것 |
| 도표 오른쪽이 잘림 | `main{max-width}` | 렌더러의 `main.wide` 토글이 해당 탭에서만 해제 |
| 탭 바꿔도 폭이 안 풀림 | 전환 경로가 둘(사이드바·이전/다음) | 클릭이 아니라 패널 class 변화를 `MutationObserver`로 감시 |
| 휠 줌이 페이지 스크롤을 뺏음 | `wheel` 무조건 preventDefault | `ctrlKey`일 때만 줌 |
| 부모 노드가 연결선에서 어긋남 | 자식 높이가 다를 때 블록 범위로 중심 계산 | 첫·마지막 자식의 **중심 평균**으로 (`mm_layout.test.js`가 잡는다) |

## 하드 규칙

- 지어낸 수치(더미 데이터)를 쓸 땐 "예시 스냅샷" 등으로 **출처를 명시**한다 — 실측인 것처럼 쓰지 않는다.
- 큰 틀을 다시 짜는 재작업 전에는 계획을 1~2문장으로 설명하고 "ㄱㄱ" 대기.
- Artifacts CSP상 외부 CDN 불가 — 폰트·JS는 전부 인라인.
- 프로젝트에 디자인 시스템 SSOT가 있으면 톤을 참고하되, 이 산출물은 실제 화면이 아니라 "기획 문서"라 앱과 시각적으로 같을 필요는 없다(구분되는 편이 "이건 초안"이라는 신호가 된다).
- **이 스킬은 제품 코드를 구현하지 않는다.** 기획 산출물이 승인되면 프로젝트가 정한 구현 흐름(Superpowers 또는 프로젝트별 실행 계약)으로 넘긴다. 삭제되었거나 존재하지 않는 프로젝트 스킬 이름을 가정하지 않는다.
- 결과는 **HTML 파일 또는 플랫폼이 지원하는 Artifact 링크**로 전달한다. 장기 보존이 필요한 제품 결정만 프로젝트의 기존 공식 문서에 승격한다. 단순 기획 요청 때문에 새 Implementation Plan을 강제로 만들지 않는다.

## 다른 세션이 만든 아티팩트를 고칠 때
