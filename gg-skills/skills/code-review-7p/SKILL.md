# 코드 리뷰

작성된 코드 변경사항을 7가지 관점에서 체계적으로 검토하고, 우선순위가 매겨진 수정 제안을 제시한다.

## 검토 절차

### 1. 변경 범위 파악
- git 저장소인 경우: `git diff` + `git diff --staged` + `git status`로 수집
- git 저장소가 아닌 경우: 최근 수정된 파일을 `ls -lat`로 식별하거나 사용자가 지정한 경로 사용
- 사용자가 특정 파일/디렉토리를 지정하면 그 범위만 검토
- 변경된 파일을 **반드시 Read 도구로 직접 읽어** 컨텍스트를 확보 (추측 금지)

### 2. 7가지 검토 항목

각 항목에 대해 코드를 읽고 이슈를 기록한다.

1. **정확성 (Correctness)**
   - 버그, off-by-one, null/undefined 처리, 비동기 race
   - 의도와 구현이 일치하는가
   - 엣지 케이스 (빈 배열, 0, 음수, 매우 큰 입력)

2. **보안 (Security)**
   - XSS (innerHTML에 사용자 입력 삽입), SQL/Command injection
   - 비밀키·토큰 하드코딩, 민감 정보 로깅
   - CSRF·CORS 누락

3. **단순함 (Simplicity)** — *CLAUDE.md 원칙*
   - 요청받지 않은 추상화/유연성/설정
   - 한 번만 쓰이는 헬퍼 함수
   - 발생할 수 없는 시나리오의 방어 코드
   - "200줄을 50줄로 줄일 수 있는가?"

4. **가독성·네이밍**
   - 변수/함수 이름이 의도를 드러내는가
   - 코드만 보고 의도가 이해되는가
   - WHAT을 설명하는 불필요한 주석

5. **에러 처리**
   - 시스템 경계(외부 API, 사용자 입력)에서만 검증하는가
   - 내부 코드에 과도한 try/catch가 없는가
   - 무시되는 에러(빈 catch)가 없는가

6. **성능**
   - 명백한 O(n²) 루프, 불필요한 재계산
   - DOM 빈번 접근, 메모리 누수 (이벤트 리스너 미해제)
   - *주의: 마이크로 최적화는 지양*

7. **테스트 가능성**
   - 비즈니스 로직과 사이드 이펙트가 분리됐는가
   - 어떤 케이스부터 테스트해야 하는가

### 3. 분류 및 보고 형식

발견 이슈를 3단계로 분류:
- 🔴 **Critical** — 버그·보안·정확성 (반드시 수정)
- 🟡 **Warning** — 단순함 위반·가독성 (수정 권장)
- 🟢 **Suggestion** — 스타일·미세 개선

각 이슈는 다음 형식으로 보고:
```
🔴 [정확성] index.html:142
   spin() 안에서 candidates가 비었을 때 idx 계산이 NaN
   → length === 0 가드를 idx 계산 직전에 추가
```

### 4. 최종 요약

리뷰 끝에 항상 다음을 포함:
- **이슈 카운트**: Critical N / Warning N / Suggestion N
- **우선순위 TOP 3** 수정 권장 (impact × 쉬움)
- **강점**: 코드에서 잘된 부분 2~3가지 (긍정 피드백)

## 행동 원칙

- **추측 금지**: 파일을 실제로 Read한 뒤 라인 번호와 함께 인용
- **코드 수정 금지**: 이 스킬은 검토와 보고만 한다 (수정은 사용자/메인 에이전트의 몫)
- **억지로 만들지 말 것**: 이슈가 없으면 "이슈 없음"이라고 명시 — 점수 채우려 가짜 이슈 만들지 말 것
- **CLAUDE.md 우선**: 단순함·외과적 수정 원칙을 가장 강한 시그널로 사용
