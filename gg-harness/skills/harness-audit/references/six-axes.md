# 6축 판정 기준

출처: 강의 Part 1 Ch04(6축) · Ch03(5 Pillars) · Ch05(11 자산) · Part 2 Ch03(프로덕션 5축) · Part 3 Ch01(AX).
각 항목 = **판정할 것** + **없으면 나는 손해**. 손해를 못 쓰면 그 항목은 이 레포에 필요 없는 것이다.

```
구조 ──→ 맥락 ──→ 계획
 ↑                  │
개선 ←── 검증 ←── 실행
```

---

## 1. 구조 (Scaffolding) — 뭘 깔아두는가

> 정량 점수는 `ai-readiness-cartography` 위임. 여기선 아래 3개만 본다.

| 판정할 것 | 없으면 나는 손해 |
|---|---|
| **사람 문서 ↔ AI 흔적 분리** (`docs/` vs `.dev/`) | AI 스크래치가 비즈니스 진실을 오염 (Ch04 §2-2) |
| **경쟁 패턴 대장** (같은 일 하는 두 경로의 목록) | **50% 룰** — 같은 일을 하는 경로가 둘이면 에이전트가 틀린 걸 고를 확률이 50% (Ch03 5-1) |
| **예측 가능한 위치** (도메인별 고정 디렉터리) | 매번 탐색 비용. 에이전트 실패의 80%가 탐색·이해 비용 (Ch05 §3-1) |

⚠️ **Consistency over DRY** (Ch03 5-2): 에이전트에겐 추상화보다 일관된 반복이 쌀 때가 있다.
"DRY 위반이니 고치자"를 자동으로 제안하지 말 것 — 사람 가독성과 에이전트 비용은 다른 축이다.

## 2. 맥락 (Context) — AI가 뭘 아는가

| 판정할 것 | 없으면 나는 손해 |
|---|---|
| **CLAUDE.md 200~300줄 이하** | 넘으면 규칙이 노이즈에 묻혀 **무시되기 시작** (Ch01 §2-4, Ch04 §3-2) |
| **경로스코프 분리** (`.claude/rules/*.md` + `paths:` frontmatter) | 평소 컨텍스트가 무거워짐. 필요할 때만 로드가 정답 (Ch04 §3-3) |
| **계층** (User → Project → Folder) | 개인 습관과 팀 규칙이 섞임 |
| **hallucinated path 0건** | 존재하지 않는 경로 인용 = 에이전트를 잘못된 곳으로 유도. stale reference 는 없느니만 못하다 |
| **tacit knowledge 가 repo 안에** | *"코드베이스에 없으면 에이전트에겐 존재하지 않는다"* (Ch03 2-4 OpenAI 원칙) |

## 3. 계획 (Planning) — 뭘 할지 정하는가

| 판정할 것 | 없으면 나는 손해 |
|---|---|
| **"해줘" 대신 계획 합의 절차가 문서에 박혀 있나** | 어긋나면 통째 재작업 (Ch04 §4-2) |
| **계획 검토 4체크** — 범위 / 기존 패턴 / 테스트 / 리스크 | 실행 단계 삽질. 계획 단계 2~3분이 훨씬 싸다 (Part0 Ch02 §3-3) |
| **모호할 때 되묻게 하는 장치** (AskUserQuestion·grilling) | 에이전트가 빈 맥락을 추측으로 채움 |
| **plan 문서의 정본 위치와 양식** | 계획이 휘발돼 같은 논의를 반복 |

> 기존 자산: `harness`(step 분해·execute.py) · `grilling`/`grill-me`/`grill-with-docs` · `product-spec-kit` · `domain-modeling`.
> 이 축은 대체로 덮여 있다. **새 스킬 제안 전에 이것들부터 확인.**

## 4. 실행 (Orchestration) — 어떻게 시키는가

| 판정할 것 | 없으면 나는 손해 |
|---|---|
| **혼자 / Subagent / Team 선택 기준** | 단순 작업에 Team = 토큰 ~7x 낭비. 큰 출력엔 Subagent 가 압도적 (Ch04 §5-1, Ch01 §4-3) |
| **worktree 격리** | 실패가 메인을 오염. 되돌릴 수 있는 환경이 Bypass 를 안전하게 만든다 (Ch01 §3-1) |
| **자율 루프의 완료 기준이 측정 가능한가** | 측정 불가능하면 루프가 영원히 돈다 (Ch04 §5-2) |
| **사람 손이 반복되는 지점** = friction | *"에이전트가 못 하는 일을 만나면, 손으로 하지 말고 도구를 만들어라"* (Ch03 Pillar III) |
| **CLI-first** | GUI·대시보드 클릭은 에이전트가 못 다룬다. **"as Code" 후보**를 찾는다 (Part2 Ch04 §6) |

## 5. 검증 (Verification) — 어떻게 믿는가

| 판정할 것 | 없으면 나는 손해 |
|---|---|
| **Generator ≠ Evaluator** (만든 컨텍스트와 검사 컨텍스트 분리) | **자기 작업을 자기가 평가하면 mediocre 도 칭찬한다** (Ch04 §6-2) |
| **검증 신호가 모델 밖에서 오나** (테스트·린트·로그) | LLM 자기평가는 같은 확률 분포에 오염됨 (Ch03 Pillar II) |
| **시작 전 완료 조건 합의** (Sprint Contract / AC) | "잘 만들어줘"는 검증 불가. `test 12개 통과`는 검증 가능 (Ch04 §6-1) |
| ⭐ **하네스 자체의 eval** | **프롬프트는 코드보다 무르다.** CLAUDE.md 한 줄 고쳤더니 리뷰 스킬이 다르게 구는 걸 아무도 못 잡는다 (Part2 Ch03 §5) |
| **위험 작업의 안전장치** — worktree · dry-run · runtime gate | 되돌릴 수 없는 사고 (Ch04 §6-5) |
| **오탐 관리** | **오탐 1건 = 신뢰 10건 손실.** 팀이 리뷰어를 통째로 무시하기 시작 (Part2 Ch02 §6-1) |

**eval 은 5개로 시작한다.** 50개 만들려다 지친다. 운영 중 발견한 실패를 하나씩 추가.
**오탐 방지 케이스 1개는 필수** — "잘 잡나"만 보면 에이전트가 모든 걸 의심해 오탐이 폭발한다.

⚠️ **기준이 재현적으로 fail 하면 기준부터 의심하라.** 2회 이상 같은 기준에서 재현되면,
그 기준을 만족하는 구현이 **존재하는지** 먼저 증명한다. "재현된다 = 기준이 맞다"는 성립하지 않는다.

## 6. 개선 (Compounding) — 어떻게 나아지는가

| 판정할 것 | 없으면 나는 손해 |
|---|---|
| **빈도 트리거가 도는가** — 같은 작업 3번 → Skill / 같은 실수 3번 → Rule | 개선이 우연에 맡겨짐. **3번이 신호다** (Ch04 §7-1) |
| ⭐ **자산 staleness 점검** | 자산이 늘수록 손으로 최신화가 불가능. 썩은 자산은 없느니만 못하다 (Part3 Ch01 §4-2) |
| **안 쓰는 자산을 치우는가** | *"좋은 하네스는 점점 단순해진다"* (Ch04 §7-2). 모델이 좋아지면 예전 가드는 불필요해진다 |
| **실패를 손코딩으로 때우지 않는가** | 5분 손코딩은 아무 자산도 안 남긴다. 같은 stall 이 다음 주에 또 (Ch03 7-5) |
| **못 맡기는 일이 생겼을 때의 반응** | "역시 사람이 해야 해" = 후퇴. **툴·컨텍스트 이슈 신호로 읽어야** 전진 (Part3 Ch01 §3-2) |

### 자가 진단 3문 (Ch04 §7-3)

| 🟢 잘 감 | 🔴 실패 징후 |
|---|---|
| 같은 말을 두 번 안 한다 | 같은 설명을 반복한다 |
| 불필요한 게 점점 줄어든다 | 하네스가 자꾸 무거워진다 |
| AI가 스스로 검증한다 | 사람이 매번 손으로 검수한다 |

## 판정할 때의 함정

- **강의에 있다 ≠ 여기 필요하다.** 1인/소수 운영이면 조직 축(Part 3 Ch02 온보딩·PR 비율)은 대부분 N/A.
- **덮인 축에 새 자산 제안 금지.** 경쟁 패턴이 곧 50% 룰이다.
- **"측정하지 않으면 개선되지 않는다"** 지만, 측정 자체가 목적이 되면 안 된다. 손해가 나는 지점만.
